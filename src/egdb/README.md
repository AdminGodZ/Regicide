# Regicide endgame database

Exact win/draw/loss values (and moves-to-conversion for up to 6 pieces) for English checkers
endgames, generated by retrograde analysis. Self-contained: depends only on `types.hpp`.

## Using it

```cpp
#include "egdb/egdb.hpp"
regicide::egdb::init(std::string(getenv("HOME")) + "/regicide-data/egdb", 4096);  // once
int n = regicide::egdb::max_pieces();                    // e.g. 7
auto v = regicide::egdb::probe(black, white, kings, stm); // Win/Draw/Loss for stm, or Unknown
int mtc = regicide::egdb::probe_mtc(black, white, kings, stm);
```

* `probe` is lock-free, allocation-free and thread-safe after `init`. It answers every position
  with at most `max_pieces()` pieces, including positions where the side to move must capture.
* `init` maps every slice file in the directory. If their total size fits in `cache_mb`, the pages
  are pre-faulted into RAM; otherwise the OS pages them in on demand.
* Repetitions inside the database count as draws.

### Moves-to-conversion (MTC)

`probe_mtc` returns, for decided positions, the number of plies before a *converting* move is
played under optimal play (winner minimises, loser maximises). A converting move is a capture, a
promotion, or a man move that advances its side's leading man to a new rank (i.e. any move that
leaves the position's subslice, see below). `0` means a converting move is due now (always the case
when the side to move has a capture). To realise a database win, play a move to a lost position
whose MTC is exactly `mtc - 1`, or a converting move into a lost position; progress is then
guaranteed because conversions only ever go to "smaller" subslices. Draws return `MTC_DRAW`.

## Design

**Canonical frame.** Positions are stored with the side to move moving down (as Black). White-to-move
positions are rotated 180° (a 32-bit bit reversal, one `RBIT` on arm64) with colours swapped.

**Slices and subslices.** A slice is a material signature `(a, b, c, d)` = side-to-move men/kings,
opponent men/kings; files `wld_abcd.rgdb`. Each slice is split by the *leading rank* of each side's
men (7×7 subslices at most). Non-capturing man moves never lower their side's leading rank, so the
subslice pair `{(abcd, x, y), (cdab, y, x)}` only depends on itself, on pairs with a higher leading
rank, on slices with more kings (promotions) and on smaller slices (captures). That makes the
working set small (largest 7-piece pair: 0.36 GB, largest 8-piece pair: 3 GB at one byte/position).

**Index.** Combinatorial number system, a bijection within each subslice:
`((ms·NO + mo)·NKS + ks)·NKO + ko` where `ms`/`mo` are colex ranks of each side's men among their 28
legal squares minus the configurations with a lower leading rank, and `ks`/`ko` are colex ranks of
the kings among the squares left empty by the men (and by the side-to-move kings). Men of the two
sides are ranked independently, so entries where they overlap are unused; they cost nothing after
compression. `egdb_gen count` checks the index against the published position totals
(e.g. 2,503,611,964 six-piece positions).

**Captures are not stored.** Positions where the side to move has a capture are don't-cares in
the files. `probe` resolves them by a capture-only negamax into smaller slices (each capture removes
a piece, so the recursion is shallow). Positions where only the *opponent* threatens a capture are
stored normally.

**Compression.** Values are run-length coded in byte tokens (`0..80` = four positions in base 3,
`81..254` = a run of one value with one of 58 roughly geometric lengths 4..1024). Don't-cares are
assigned whatever extends the current run. Positions are grouped in blocks of 1024 indices; a u32
offset per 32 groups and a u16 offset per group give O(1) access to the block, followed by a short
token scan. Subslices whose known values are all equal are stored as a single constant. MTC tables
use the same layout with a literal/repeat token stream.

**Generation.** For each subslice pair: (1) an initial pass resolves every position from
information outside the pair (captures, promotions and leading-rank-changing man moves are looked up
in finished tables via `probe`) and stores, for undecided positions, the number of moves that stay
inside the pair (+1 if a converting move reaches a draw); (2) parallel retrograde passes propagate
decided positions to their predecessors (un-moves of the side that just moved), turning a
predecessor into a win when a successor is lost and decrementing its counter when a successor is
won (counter 0 = loss); (3) whatever is still undecided is a draw. The pass number at which a
position is decided is its MTC. Frontier bytes are found eight at a time; predecessor updates are
CAS operations, batched with software prefetch. Each finished subslice pair is written to
`parts/` so an interrupted build resumes where it stopped.

**File format.** `FileHeader` (64 bytes: magic `RGCEGDB1`, kind, material, file size, FNV-1a
checksum of the rest), `SubRecord[nsub]` (64 bytes each), then 8-byte aligned arrays. All fields are
fixed-width little-endian integers, so files are byte-identical across macOS, Linux and Windows and
can be copied between machines (`egdb_gen manifest` verifies checksums).

## Validation

* `egdb_test`: perft 0..10 with the module's own move generator, index round trip for ≤4 pieces,
  position counts for ≤6, a fresh 2–4-piece build verified *exhaustively* (stored value = minimax of
  successor values; MTC satisfies its recurrence), known endings, resumability.
* `egdb_test --data`: the same one-ply consistency on samples of every slice of the real database.
* `tools/chinook/xcheck.sh`: compares every 2–4-piece position (both colours to move, positions
  without a capture for either side, as Chinook requires) against the Chinook database through the
  original lookup code in Cake 1.22's `db.c` (patched for LP64 in a scratch directory, never copied
  into this repository).

## Future 8-piece build (not started; run only on request)

Prerequisite: the complete 2..7-piece set in the target directory (`egdb_gen manifest` exits 0,
`egdb_test --data` passes). Then, in that directory's parent (e.g. WSL on Win11-AdminGod):

```
nohup egdb_gen build --max 8 --threads 8 --dir ~/regicide-data/egdb > ~/regicide-data/gen8.log 2>&1 &
# or the most valuable families first:  ... --sides 44   then   ... --sides 53
```

* Work: 447.2 G index entries vs 37.0 G for 7 pieces (×12.1). Family shares: 4v4 28%, 5v3 44%,
  6v2 22%, 7v1 6%. Each family depends only on itself and on 7 pieces.
* Time at 8 threads: 7 pieces took 639 s on Win11-AdminGod (1134 s on the loaded Mac), so expect
  ~2.2 h nominal and ~3–4.5 h allowing 1.5–2× for larger tables and longer passes (4v4 alone ~1 h,
  5v3 ~1.5–2 h).
* RAM: largest subslice pair 3.0 GB (one byte per position) plus the mapped 7-piece files (~0.7
  GB) and encoder buffers; plan for ~5 GB peak.
* Disk: ~5–9 GB for the 8-piece WLD files (7 pieces compress to 0.158 bits/entry), plus transient
  part files of the slice in progress; keep ≥ 20 GB free.
* Resumable: rerun the same command after an interruption. Validate afterwards with
  `egdb_gen verify --slice abcd --samples 50000` for each new 8-piece file and `egdb_gen manifest`.
